# ADR-015: 跨进程看门狗的心跳控制面必须带外处理，任何入站消息均计为存活证据

- **状态**: 已接受
- **日期**: 2026-08-05
- **相关 story**: 2026-08-02-builtin-agent（BUG-008）
- **相关 REQ**: REQ-AGENT-005（看门狗生命周期）

## 背景

ADR-014 决策了 agent 运行时独立子进程 + 主进程看门狗（ping/pong 心跳 + exit 检测 + 重启）。上线后真实使用暴露：飞书流式回复发一半卡死——卡片停在「生成中...」，短回复正常、长回复必现。

根因：worker 子进程的消息处理是**全局串行队列**，主进程发来的 ping 被排在 `await` 整个 LLM 生成的 prompt 后面 → 主进程 6 秒收不到 pong → 看门狗 SIGKILL 一个健康但忙碌的进程 → 流式中途断裂。REQ-AGENT-005 标准 2 的意图是检测**真崩溃**（进程卡死/退出），而实现把「忙碌」误判为「崩溃」。

这揭示跨进程监督的一个通用陷阱：**心跳响应若与工作负载共享调度通道，工作负载本身就是心跳的最大干扰源**——负载越重（越需要被监督），心跳越容易超时（越容易被误杀）。监督逻辑在最需要它的时刻失效。

## 决策

任何「看门狗 + 被监督进程」结构（不限于 agent 子进程）：

1. **心跳控制面带外处理**：ping/pong 不进入被监督进程的工作队列，收到立即回应（事件循环可用的前提下），与工作负载零排队依赖。
2. **任何入站消息均计为存活证据**：监督方收到被监督方的**任何**消息（含业务事件，如流式 session-event）即刷新最后存活时间，不只看 pong——进程在说话就是活着。
3. 看门狗杀死条件收紧为「**完全静默**超时」+「exit」，不再隐含「未及时响应控制消息 = 崩溃」。

## 后果

- agentService/worker 已按此修复（BUG-008）：worker ping 带外即时回 pong；主进程任何子进程消息刷新 lastPongAt；回归测试以真实 spawn + 横跨 6s 超时窗口的长生成断言不重启。
- 未来新增看门狗/健康检查（如 channelManager 长连接监督、flow 执行超时）按同一模式设计：监督信号与业务负载必须无排队依赖。
- 代价：带外回应不能发现「事件循环完全阻塞」型卡死（同步死循环占住事件循环时 pong 也发不出——此时心跳确实超时，行为正确）；该场景由「完全静默」条件覆盖，语义一致。

## 替代方案

- **A. 心跳进工作队列但调大超时**：负载不可预知（LLM 生成分钟级），超时阈值无法兼顾「快速发现真崩溃」与「不误杀长任务」。
- **B. 工作进度上报作为心跳**：要求 worker 在生成期间主动汇报进度；耦合业务逻辑与监督逻辑，且静默型卡死仍需独立心跳。
