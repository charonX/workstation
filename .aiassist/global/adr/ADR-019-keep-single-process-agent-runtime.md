# ADR-019: 维持单进程——PI agent 运行时暂不拆分（会话隔离缓建，附重估触发条件）

- **状态**: 已接受
- **日期**: 2026-08-08
- **相关 story**: 2026-08-07-pi-agent-consolidation
- **相关 REQ**: REQ-AGENT-045（文档断言）；对齐 REQ-AGENT-005（不变关系）

## 背景

ADR-014 已把内置对话 agent 运行时定为「SDK 独立子进程」形态：**一个** worker 子进程承载全部对话空间会话（飞书/UI 通用/UI 项目），主进程 `agentService` 看门狗监督、崩溃重启经 JSONL 恢复。ADR-014 决策时「每空间一子进程」（RPC 形态）已因多对话空间并发过重而否决。

2026-08-07 consolidation 访谈再次拷问进程隔离模型（③ 进程隔离模型议题）：是否进一步拆分——按空间拆进程、或为未来多租户空间隔离做铺垫？用户对痛点轴的回答是 **(d) 从未真崩过，预防性结构洁癖**；并明确「如果未来做了保活处理后，全部重新拉起应该也没有太大的问题」。

## 决策

1. **维持单进程**：PI agent 运行时保持 ADR-014 的单一 worker 子进程形态，本决策不建造任何分进程（按空间/按租户拆进程）；REQ-AGENT-005 / ADR-014 / ADR-015 均不因本决策改变。
2. **①落地后全量重启恢复代价可接受**：本 story 落地会话生命周期规则（idle TTL 1h 淘汰 + LRU 上限 50 + 同组单活冷却 + JSONL 透明懒恢复 + 水合窗口规则化）后，崩溃/全量重启的恢复形态为——**窗口内活跃会话重水合**（JSONL mtime ≤ 1h 的行下发 session-config，`SessionManager.open` 恢复）+ **历史行透明懒恢复**（未水合行首次交互走同一恢复链路）。恢复是透明的（用户续聊无感知），代价仅为冷恢复的首次延迟（M1 待 QA 实测阈值），在「没痛感不大动」原则下可接受。
3. **重估触发条件**：出现以下任一情形时回来重谈分进程——
   - **真实崩溃发生且影响不可接受**：出现实际崩溃事故，且「worker 整体重启 + 全量恢复」的影响被证实不可接受（如会话恢复丢失、用户可见中断超阈值）；
   - **空间间隔离需求出现**：出现跨空间隔离需求（如多租户、互不信任的会话并发、单会话故障不得波及同进程其他会话的产品要求）。
4. **不变关系声明**：REQ-AGENT-005（看门狗心跳/崩溃重启/JSONL 恢复/restarting 语义）、ADR-014（SDK 独立子进程形态）、ADR-015（心跳控制面带外、任何入站计存活）为本决策的**硬约束**，不因「维持单进程」而改变；本 story 复用其恢复语义，不新造。

## 后果

- 会话共享一个 worker 进程：单会话致命错误（OOM/native crash）仍走 ADR-014 既有「worker 崩溃 → 看门狗重启 → 水合窗口 + 懒恢复」路径——恢复形态已由决策 2 论证可接受，不构成分进程理由。
- 长期内存有界靠会话生命周期规则（TTL/LRU/同组单活）实现，不靠进程级隔离；「内存单调涨」问题由规则收敛而非架构拆分解决。
- 收益：零启动延迟增量、零恢复编排复杂度、REQ-AGENT-005/ADR-014/ADR-015 契约零变更——符合「无事故痛感不大动」的用户拍板。
- 代价：若未来触发条件成立，分进程将是一次契约面变更（恢复语义、IPC、看门狗均受影响），改造成本集中在 worker/agentService 两侧——重估时第一刀落在会话生命周期模块（访谈 D2 已预留）。

## 替代方案

- **方向 A. 分进程建造（爆炸半径隔离）**：按空间/租户拆进程换取隔离强度；取舍为隔离性 vs REQ-AGENT-005 契约变更 + 启动延迟（每空间一常驻进程，个人桌面应用过重）+ 恢复编排复杂度。访谈结论：**不推荐（本轮）**——用户答 (d) 无事故痛感，降级为本决策记录 + 重估触发条件（D1）。
- **每空间一进程（RPC 形态）**：ADR-014 已否决（多对话空间并发 = N 个常驻进程过重、工具注入能力受限）；本决策沿用该否决。
