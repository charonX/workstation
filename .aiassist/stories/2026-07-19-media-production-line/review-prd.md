## 警告项（建议但不阻塞）

- [ ] **维度：用户故事 — OP-6 的"schedule 到点"在 headless 下不成立**
  - 问题：OP-6 步骤 1 写"App 未启动，CLI 执行 `task run` / schedule 到点 → CLI 自起 headless server"。但 schedule 到点触发的前提是 server 进程在跑（调度器随 server 生命周期注册，稳定块 1 自己也这么写）。App 未启动、也无常驻 server 时，cron 到点不会有任何触发。现状措辞容易让结晶产生"headless 下 schedule 也能无人值守到点触发"的误读。
  - 建议：把 OP-6 拆清两种语义：① CLI 手动运行自起 headless server 且数据落盘（本 story 验收锚）；② 无人值守定时触发依赖常驻 server 或由外部 cron 调 CLI（若想要后者，需显式写入范围，否则声明为后续 story）。稳定块 2 本身清晰，只需修操作流表述。

- [ ] **维度：稳定块 — 场景 A 日报的内容来源语义未锁死**
  - 问题：稳定块 4 写"主题 × 内容源 → agent 收集+合成"，§2 写"抓取/搜索/合成"，访谈隐含假设 4 说 agent 可调外部搜索 API。日报究竟是"仅从已登记内容源聚合"还是"agent 围绕主题自主搜索"，PRD 未显式声明。测试上没问题（agent seam 用 mock，验收锚在产物文件），但用户故事 2 的真实使用价值取决于这个决策，且它影响 flow 配置形态（移动块 6）。
  - 建议：结晶前显式一句话：场景 A 验收只要求"引用内容源"路径，还是同时声明"搜索能力由 skill 层尽力提供、不进验收"（与 x/wechat 同款处理）。后者似乎符合本意，但应白纸黑字。

- [ ] **维度：稳定块/复杂度 — 砍项预案未从访谈笔记带入 PRD**
  - 问题：interview-notes「矛盾/风险 #3」给了明确预案——结晶时若太厚，先砍日报飞书推送（只留落盘），再砍内容源类型（只留网页）。PRD §9 自评 complex、9 个稳定块 + 3 个新模块 + 1 个外部依赖，厚度风险真实存在，但预案没有写进 PRD。
  - 建议：把砍项预案补进 §13 补充说明，结晶超厚时直接援引，不用重新决策。

- [ ] **维度：稳定块 — 引用的 ADR-003/004 实体文件缺失（全局文档卫生）**
  - 问题：稳定块 9 引用 ADR-003/004 作为 skill 架构依据；`adr/README.md` 索引中两者均为"已接受"，但 `adr/` 目录下只有 ADR-001/002/005 三个实体文件。
  - 建议：在 /domain-model 或 /tech-design 阶段顺手补齐 ADR-003/004 文件（属全局维护，与本 PRD 内容无关，不阻塞）。
