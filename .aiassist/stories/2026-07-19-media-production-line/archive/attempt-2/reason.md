# Archive reason — attempt 2

## 根因诊断

错误假设活在**方案层 / 需求层**（稳定块 12），不在初衷层。

- **初衷仍成立**：用户需要在飞书里发链接/消息后，系统自动把内容沉淀到项目素材库（链接速存场景）。
- **错误假设**：我们认为必须在 `feishuMessage` 触发节点里提前解析出 `url`，并把它作为固定输出变量暴露给下游。
- **推翻理由**：
  1. 过度提前解析会限制节点通用性。用户可能发送不含 URL 的消息，也可能后续流程需要原始文本做其他处理（如摘要、分类）。
  2. 节点语义应该与通用 trigger 对齐：只负责"把外部事件映射成变量"，不负责对事件内容做业务解析。
  3. 当前实现导致没写 defaultValue 的变量在下游选不到（已作为 BUG-004 修复），说明"固定输出 + 提前解析"的设计在 UX 上容易出问题。

## 新方向

把 `feishuMessage` 节点改为**通用原始消息载体**：

- 固定输出变量改为原始消息文本（如 `text`），以及必要的元数据（`sender`、`messageId`）。
- `url` 提取逻辑从 `feishuChannelAdapter` / `imRouter` 前移到下游：由链接速存模板里的 agent/skill 自己从 `text` 中解析链接。
- `imRouter` 不再以"无 URL 不触发"作为硬分支；是否触发由 flow 自身决定，或者保留一个可选的"需要 URL"过滤作为配置项（待定）。
- 链接速存模板默认 agent prompt 从 `{{n1.url}}` 改为基于 `{{n1.text}}` 自己提取 URL。

## 下次应避开的坑

1. 不要把业务解析逻辑塞进触发节点；触发节点只映射事件字段。
2. 设计固定输出变量时，先问"这条消息里最不可缺的原始字段是什么"，而不是"下游第一个业务步骤需要什么"。
3. 变量选择器必须在 PRD 签核前就与 UX 原型一起验证，不能留到 QA 才发现。
