# 访谈笔记 — 2026-07-19-media-production-line

> 触发材料：
> - [用 Codex + Remotion 实现无痛自媒体视频日更](https://x.com/Zesee/status/2072417062165635433)（模板+数据→视频的生产线方法论）
> - [泊舟：用AI做视频一个月的心法](https://x.com/bozhou_ai/status/2074790399789732348)（逐字稿→音频→字幕驱动画面→低画质调试；模板/素材/纠偏沉淀为 skill；[开源 skills](https://github.com/bozhouDev/video-skills-toolkit)）

## 核心问题

workstation 撑不起「模板+数据→媒体产物」这类生产线工作流。用户的内容生产分四段：**收集**（阅读时攒素材/方向）→ **想法**（闪光点是创作起点）→ **文章**（收集相关内容、整理、排版、输出）→ **视频**（泊舟心法链路）。本 story 切片到第一段「收集」，把四段抽象为 flow 节点编排的愿景由此起步。

## 用户画像

- 用户本人，solo 内容创作者，dogfooding：系统做出来首先是给自己每天用的。
- 日常：阅读（X/公众号/网页）→ 收集素材 → 写文章（现行日常）；视频是目标态，尚未跑起来。
- 阅读与触发场景在手机和桌面，飞书是顺手工具。

## 关键边界

1. **第一刀 = 收集段**；想法/文章/视频段均为后续 story。
2. **双触发**：cron 定时（场景 A：每天 10:00 AI 科技日报）+ 飞书 IM（场景 B：发链接→转 markdown 速存）。
3. **产物主锚点 = 项目素材库文件（markdown）**——下游文章/视频 flow 消费文件，系统验收锚在文件上；飞书云文档为同步副本。
4. **飞书一身三任**：触发源（发链接）、投递通道（收日报/确认）、沉淀地（云文档）。第一通道只做飞书，长连接模式（无公网 IP）。
5. **内容源是一级实体**（X、公众号、网页 + 搜索）；X/公众号抓取难度高，agent 尽力而为，**不进验收标准**。
6. **基础设施顺带补齐**：调度真正接通（cron→flow，当前是空壳：`taskService.js:550` 只有订阅者没有发布者）、headless 模式 DB 落盘（`db.js:9-14` 默认 `:memory:`）。
7. 通用 webhook 端点不做（IM 通道覆盖该需求）。
8. 四段抽象大概率 = flow 编排 + agent 节点 + skill 扩展，未必需要新节点类型（留 /tech-design 判定）。

## 隐含假设

1. 用户在飞书里发链接/收日报是顺手的（阅读场景与飞书重合）。
2. 下游消费的是文件系统素材库，不是数据库记录。
3. 收集能力主要靠 **skill 扩展**（抓取、搜索、日报合成、飞书同步）实现，系统内核只新增触发层（调度+IM 通道）与内容源实体。
4. agent 节点（Claude Code，bypass 权限）可以调外部服务（搜索 API、飞书 OpenAPI）。
5. 验收环境可注入飞书应用凭据（App ID/Secret）。

## 矛盾/风险

1. **X/公众号抓取难度**：X 需 API 或抓取技巧；公众号几乎无公开抓取通道（一般绕道 RSS 代理）。→ 不进验收，skill 层尽力而为。
2. **"检查全绿 ≠ 产物正确"**（泊舟教训）：验收必须断言真实产物内容（文件存在且结构/内容符合预期），不能只看执行状态 success。呼应 STANDARDS.md「文件系统副作用必须写进 REQ 并用真实 I/O 断言」。
3. **story 偏厚**（触发层 + 内容源实体 + 产物层 + IM 通道）：预案——结晶时若太厚，先砍日报飞书推送（只留落盘），再砍内容源类型（只留网页）。
4. 飞书凭据外部依赖：验收需要可控的注入方式和 mock 策略。
5. 个人微信接入是灰色地带（第三方桥接有封号风险），已明确排除；"微信开放 CLI" 实为企业微信 CLI（@wecom/cli，2026-03 开源），本期不做。

## 候选方向

### 方向 A：收集管线完整 story（场景 A + B 一起）
- 适用场景：两个触发场景共用同一套地基（触发层/收集层/产物层），合建省一次返工；IM 双向通道同时解决 B 的触发与 A 的投递。
- 主要取舍：story 偏厚，用砍项预案控制。
- 推荐度：**首选（用户已确认）**

### 方向 B：只做场景 A（定时日报）
- 适用场景：求最快见绿。
- 主要取舍：IM 通道这个扩展性最强的能力没动，"主动喂系统"链路未验证，下 story 重开触发层。
- 推荐度：备选（A 太厚时的退路）

### 方向 C：先做 IM 通道 + 场景 B
- 适用场景：通道先行对长期最值。
- 主要取舍：调度继续空转，"每天自动喂我日报"的生产线感延后。
- 推荐度：不推荐

## 确认方向

最终确认的方向：**方向 A，IM 第一通道押飞书，产物沉淀增加飞书云文档镜像**。

确认意图（用户显式 yes："没问题"）：

- **Outcome**：workstation 跑通收集段——内容源实体管理 + 双触发（cron/飞书 IM）+ agent 收集（抓取/搜索/日报合成）+ 产物沉淀（项目素材库 + 飞书文档副本）+ 飞书双向送达；顺带补齐调度接通与 headless DB 落盘。
- **User**：用户本人，每天真实使用。
- **Why now**：方法论文章验证可行性；workstation 编排骨架已在但触发/产物层空转；飞书长连接 2026 年已成熟。
- **Success**：① 每天 10:00 自动产出 AI 科技日报，写入项目文件 + 飞书文档，飞书收到；② 飞书发链接给机器人 → 正文转 markdown 存进项目素材库 → 机器人回复确认。
- **Constraint**：飞书优先（长连接、无公网 IP）；产物主锚点是项目文件；X/公众号不进验收。
- **Out of scope**：想法/文章/视频段；个人微信/企业微信；通用 webhook 端点；多平台发布自动化；视频渲染（Remotion/ffmpeg）；Codex provider；执行流式/审核门等 P2 项。

确认理由：两个触发场景是同一触发层的两面，分开做等于同一层开两次刀；IM 双向通道一笔投资两处兑现。

## 最窄的切入点

先把场景 A 的骨架竖起来：调度接通 → 内容源（先网页/RSS 类）→ agent 收集+日报合成 → 项目文件落盘；再加飞书（投递 → 触发 → 文档镜像）；场景 B 复用同一收集/产物层。
