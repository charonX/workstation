## 核心问题

PI agent 对话在本机 UI 会话区只有纯文本回显（`MessageList.jsx:41` 直接 `{m.text}`），
读长回复费劲、工具调用毫无呈现、代码块无高亮——"能用但不好读"。
参考：https://github.com/agegr/pi-web（pi coding agent 的本地 Web UI，3.8k stars）。

## 用户画像

本机单用户；对话场景代码密集（agent 写代码/改配置/查日志）；飞书侧已有 CardKit 卡片流式（已定型，非本期痛点）。

## 已确认决策

### D1. 主菜 = 输出呈现层（2026-08-08 人拍板）

用户原始意图四件套（丰富 agent / 优化输出 / 查插件 / 参考 pi-web 样式）分解为三个独立子系统：
①输出呈现层 ②能力层 ③产品形态层 + ④调研任务。**主菜 = ①**，其余不本期。

### D2. 渲染深度 = A+B 全量（人拍板）

- **GFM 全量**：表格、任务列表、删除线、链接、引用、代码块（对标 pi-web：remark-gfm，`singleTilde:false` 防 CJK 数字区间误伤）
- **代码高亮**：围栏语言标记为主 + 无标记自动检测兜底；**主题跟随全局深浅切换**（双主题）
- **Mermaid 图表**（```mermaid 围栏）+ **KaTeX 公式**（remark-math + rehype-katex 等价物）
- 实证修正：pi-web 实际**没有**代码高亮也没有 Mermaid（lib/markdown.ts 源码证实，README 有夸大）——我们的 A+B 超过它

### D3. HTML 本期不做（人拍板）

agent 输出的原始 HTML（`<table>`/`<style>` 等）一律按 **Markdown 转义**处理——不做 rehype-raw/白名单管线，零 XSS 面（比 pi-web 的 sanitize 路线更简更安全）。省掉 sanitize 白名单维护面。

### D4. 工具调用 = 折叠式内联（人拍板）

- `tool_execution_start/end/error` 事件（REQ-AGENT-012 标准 4 已有数据）→ 消息流内折叠块
- 默认收起：工具名 + 输入摘要（如 `write file.txt`）
- 展开：完整输入 / 输出 / 耗时
- **错误（tool_execution_error）默认展开 + 标红**（agent 出问题要立刻可见）

### D5. 流式策略 = 实时增量渲染（人拍板）

每个 `text_delta` 直接喂渲染器；未闭合语法暂时显示字面量（`**粗体` 先显示原文），闭合即渲染。
业界标准（Claude/ChatGPT 同款）；半渲染态（代码块中间无高亮、表格未完成无边框）是可接受权衡。

### D6. 历史消息 = 统一管线（人拍板）

- 旧消息（纯文本 `m.text`）与新消息同一渲染器——纯文本渲染后视觉一致；带 Markdown 语法的旧消息"升级后变样式"是特性（存的就是 Markdown 源文本）
- **消息存储契约不动**（agent_sessions/消息文本无 schema 变更）
- **工具块仅实时呈现、不落历史**（tool_execution 是流式事件，历史无结构化留存；回看历史工具全貌延后）

### D7. 技术路线 = 方向 A（人拍板）

react-markdown + remark-gfm + remark-math/rehype-katex + Mermaid 组件 + 代码高亮（标记+自动检测，双主题）；
HTML 全转义；工具折叠块组件消费 tool_execution_* 事件；流式实时增量。

### D8. 图片显示（2026-08-08 人补充，收尾确认时）

消息内**图片/附件显示本期做**——agent 回复里引用的本地图片路径要显示为图片
（markdown `![alt](path)` 与裸路径均需处理；本地路径 → 项目/工作区文件读取渲染）。
图片引用不在 Out of scope 内。

### D9. 暗色主题独立配色（2026-08-08 人补充，收尾确认时）

Mermaid/图表与高亮在**暗色主题下用单独一套配色**（显式定义暗色方案，非全局 token 自动映射）——
浅色/暗色各一套显式配色，跟随主题切换。

## 关键边界

1. 呈现层仅本机 UI 会话区；飞书侧（CardKit 卡片）不动
2. 消息存储契约不动；工具块不落历史
3. HTML 原始内容转义（不渲染）
4. 其余意图（能力层/产品形态层/插件调研）明确不本期——但"查 pi 插件"可作为未来 story 的输入记录

## 隐含假设（BUILD 前需验证）

1. **Mermaid/KaTeX 依赖的可行性**：纯前端渲染库（mermaid.js / katex）在 Electron renderer 可正常打包运行（无原生依赖）
2. **代码高亮自动检测**：无语言标记时的检测质量可接受（Shiki 的 grammars 匹配或 highlight.js 启发式；裸日志片段兜底 plaintext）
3. **流式实时渲染性能**：长消息（几百 KB）逐 delta 渲染无卡顿（React 渲染节流/批处理）
4. **既有流式契约兼容**：text_delta/text_end 事件流形态不变，仅渲染层升级（SSE/消息事件契约零改动）

## 矛盾/风险

1. **半渲染态的可接受度**：实时增量下代码块中间闪烁/表格未完成——已定为可接受权衡，但 E2E 断言需规避时序敏感（断言最终态而非中间态）
2. **依赖引入面**：react-markdown 生态 + mermaid + katex + 高亮库 ≈ 4-5 个新依赖——包体增长、版本兼容（Electron 打包）需验证
3. **工具块时序**：tool_execution 与 text_delta 交错到达——消息流内的块插入顺序要与事件序列一致（折叠块组件消费事件流需按序）

## 候选方向

### 方向 A：React DOM 渲染管线（首选，已确认）
- react-markdown + remark-gfm + KaTeX + Mermaid + 高亮（双主题）；HTML 转义；工具折叠块
- 取舍：4-5 个成熟纯前端依赖；流式半渲染态需处理

### 方向 B：自研轻量 Markdown 子集
- 零依赖但 GFM 全量自研成本高、易出解析 bug
- 推荐度：不推荐

### 方向 C：富文本编辑器框架（TipTap/ProseMirror）
- 功能过剩（对话是展示非编辑）、包体大
- 推荐度：不推荐

## 确认方向

最终确认的方向：**方向 A**（人"方向A吧"显式确认）

- **Outcome**: 会话区对话从纯文本升级为富呈现——GFM（表格/任务列表/删除线）+ 代码高亮（围栏+自动检测，双主题）+ Mermaid（暗色独立配色）+ KaTeX + **图片显示（本地路径渲染）** + 工具调用折叠块（默认收起、错误展开标红）+ 流式实时增量渲染 + 历史统一管线
- **User**: 本机 UI 会话区使用者（读长回复、看工具行为）
- **Why now**: 纯文本"能用但不好读"；工具调用零呈现；pi-web 证明该呈现是 pi agent 工作流标配
- **Success**: E2E 渲染断言（GFM/高亮/Mermaid/公式/图片/折叠交互）；流式实时无不可接受闪烁；HTML 全转义零 XSS 面；既有 662+ 测试零回归
- **Constraint**: 消息存储契约不动；飞书侧不动；HTML 本期不做
- **Out of scope**: HTML 渲染 / 飞书侧 / 存储升级 / 历史工具块回填 / 编辑器能力 / 长对话虚拟化 / 能力层与插件调研

## 最窄的切入点

**Markdown 管线接入**（GFM + 转义 + 流式实时）先行——纯渲染升级、无新依赖面外的复杂度；
代码高亮 / Mermaid / KaTeX / 工具折叠块按依赖序跟进（高亮 → 折叠块 → Mermaid+KaTeX）。
