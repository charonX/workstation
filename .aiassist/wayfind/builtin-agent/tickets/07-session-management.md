# 07 — 对话 session 的模型：粒度、生命周期、跨入口连续性

- **Type**: grilling
- **Mode**: HITL
- **Status**: resolved
- **Blocks**:
- **Blocked by**:

## Question

用户明确要求"需要有 session 管理"。session 的模型需要定清楚：

- **粒度**：一个 session 绑定什么？飞书用户 open_id？飞书聊天（单聊/群聊）？项目维度？
- **生命周期**：空闲多久过期？应用重启后是否持久化恢复（存在哪——SQLite？）？
- **上下文流转**：多轮对话历史如何进入任务执行（作为 agent 的上下文输入）？跨 session 的"了解正在进行的任务"是否只是查 execution 而非靠记忆？
- **跨入口**：飞书会话与 UI 面板的 session 是否共享（同一对话可在两个入口连续）？

## Resolution

2026-08-02 用户拍板：

1. **粒度：按对话空间分**——飞书单聊 / 每个群聊 / UI 面板各一个 session；上下文隔离不串；单用户绑定下空间内即本人。
2. **生命周期：持久化 + 不超时 + 显式重置**——对话历史持久化到 SQLite（应用重启可恢复"接着聊"）；不设空闲超时；提供显式重置入口（如 `/reset` 命令，与 08 票命令集联动）。
3. **上下文压缩**——对话过长时压缩历史（滚动摘要），控制 token 成本；压缩策略为 story 设计点。
4. **不流转**——session 上下文只用于理解指令；任务执行独立，执行状态/历史靠 CLI 查询命令获知（"了解进行中的任务" = 查 execution，不靠记忆）。
